# Prompt：全量代码审查（接线 / 假绿 / 硬编码优先）

你是本机的一名资深代码审查员。下面会给你一个**已经实现并自称已验证**的项目源码。请审查**代码本身**，不要复述文档里的结论，也不要把文档的自我评价当成事实。

## 项目结构（先看这个，避免误读）

三个交付物，同仓库：

1. `extension/` —— Chrome MV3 扩展（纯 JavaScript + esbuild）。`src/sw/`（service worker：抓取、右键菜单、ops、审计）、`src/sidepanel/`（侧边栏面板 + `/ag/agent` 工具桥 + 白盒探针钩子）、`src/lib/`（URL、协议生成物、dev-config）、`src/content/extract.fn.js`（注入页面的抽取器）。
2. `dsh-plugin/` —— DSH 进程内插件（cordis）。**host 半**在 `src/host/`（`/ag/*` HTTP 路由 + WS hub + 工具注册 + 落盘 + 保留策略 + 审批闸门 + 审计），**client 半**是 `lib/client.js`（由 DSH 页面通过 `window.__ModuleLoader__.load()` 加载的 CJS 闭包工厂，**手写产物，没有构建脚本**）。
3. `native-host/` —— native messaging 宿主（Node，Chrome 直接 spawn）。

关键事实（决定了"接线"容易错在哪）：

- 桥接通道有两条 WS：`/ag/client`（**DSH 页面**持有：接收 attach 推送、上报「看左边」意图、回 ack）与 `/ag/agent`（**扩展侧边栏文档**持有：接收 capture-request 与工具调用）。
- **一个用户通常有两个 DSH 页面半同时连着**：主 GUI 标签页 + 侧边栏 iframe 里那一份 DSH GUI（面板本身内嵌 DSH GUI）。它们共享同一个会话存储，但是**两个独立的 React 应用**。
- 抓取链路：扩展抓页 → `POST /ag/attach` → 落盘 → 推给页面半 → 页面半把 `@文件` 写进某个会话的草稿。
- 「看左边」链路：用户在 DSH 输入框打「看左边」→ **页面半**嗅探（ADR-11：扩展读不到跨域 iframe 的输入框）→ 发 `intent` → host 转成 `capture-request` 发给扩展 → 扩展抓页 → attach 回到页面半。
- 门禁：`npm run check`（协议一致性 + 19 条反模式规则 + 单测 + 构建 + 产物端口一致性）、`npm run probe:*`（真 Chrome 探针）、`tests/unit/*.mjs`（node 直跑的断言脚本）。

## 你的任务

找出**真实缺陷**，按严重度排序。特别关注这三类（这是用户点名要的）：

### A. 接线问题（wiring）

- 事件/通道的**生产者和消费者是否真的对得上**：谁发这个帧、谁读它？有没有发了但**没有任何 handler** 的帧（或反之：等了永不到来的帧）？
- 数据流在跨模块传递时**是否丢了字段**：某处读 `payload.x` 但上游从来不设 `x`；某处按字符串枚举比较，而另一端产生的是**不同拼写**（下划线/连字符）、**不同类型**（number vs string）。
- 生命周期/时序：连接、断开、重连、心跳、超时路径上的资源与状态是否一致；是否存在"设了状态但没人清"的分支。
- 两个页面半、多个 socket、多次投递这类**多实例**场景下，行为是否仍然正确、是否只落一次。

### B. 假绿问题（false-green）

- 测试**是否真的在测被测对象**：断言是否可能因为桩/默认值/空数组/`undefined` 而恒真？有没有 `|| true`、只断言"不抛异常"、只断言"数组存在"这类空断言？
- 有没有断言跑了**白盒 hook 或测试专用分支**，而真实用户路径走的是另一条？（例：探针调用插件暴露的测试钩子，钩子内部的行为与真实链路不同。）
- 有没有"断言的目标值被改成了实现的实际值"（为了绿灯改期望），或断言只覆盖成功分支、错误分支从没被触发？
- 测试之间是否会**互相污染**（共享端口/共享文件/共享全局状态/顺序相关）？

### C. 硬编码问题（hardcoding）

- 端口、路径、密钥、域名、超时、上限被写死在多处且**不一致**（改一处漏一处）。
- 与运行环境耦合的常量（例如把测试端口/测试密钥烤进**发布产物**）。
- 逻辑上应该可配置却写死、或同一语义在多处各写一份（漂移风险）。

1. 每条发现给出：**文件:行号**（逐字引用关键代码片段）→ **为什么是缺陷**（触发路径/后果）→ **如何验证**（具体命令或最小复现步骤）→ **严重度**（BLOCKER / MAJOR / MINOR）。
2. 区分【已确认】（你从代码里能直接证明）与【可疑待验】（需要跑起来才能确认）。**不要把可疑写成已确认。**
3. 明确列出你**没有**覆盖的部分（如果上下文被截断或某目录没给全，如实说）。
4. 不要报纯风格问题（命名、空行、注释错别字）；除非它导致误解进而会引发缺陷。
5. 最后给一个"如果只能修 3 处，修哪 3 处"的结论。
